## Gap assessment against the requested business rules

| Area | Evidence in this repository | Required planning work |
| --- | --- | --- |
| Identity, roles, assignment, and visibility | No authentication, user, role, or assignment model. | Establish the identity provider/session contract; model student/mentor roles and explicit mentor–student assignment. Apply authorization in every resource query and mutation, including direct-ID access. Mentor directory access must not imply access to unassigned students' activities. |
| Activity lifecycle and review authority | No activity or transition logic. | Define persisted states (`to_start`, `in_progress`, `in_review`, `needs_correction`, `completed`) and implement allowed transitions in a domain/service layer. Restrict start/submit to the owning student and review/complete/correction to the assigned mentor. Require a correction reason; reject student edits after completion. |
| Submission history and deadlines | No submissions, versions, or dates. | Store immutable submission versions and the precise version reviewed. Record submission time independently from review time; derive lateness from submission time versus the activity deadline so a timely submission stays timely when reviewed later. Confirm policy for deadline edits/time zone and file/link payloads. |
| Concurrent edits and duplicate requests | No mutation or concurrency contract. | Use optimistic concurrency (revision/`updated_at` precondition) for activity edits and return a conflict rather than silently overwriting. Make submit requests idempotent with a client idempotency key/unique constraint. Bind review to a submission version and prevent stale-version review from completing a newer submission. Use transactions around state changes, version creation, and event/outbox writes. |
| Dashboard and filters | No query, aggregate, or dashboard support. | Compute counts/progress only over the caller's authorized activities. Count only `completed` as complete. Reuse the same status, date-window, and filter predicates for cards and their corresponding lists; specify which activity date drives each interval. |
| Conversations, notifications, and email settings | No messaging, notification, or email code. | Add conversation membership checks; keep notification read state separate from conversation read state. Generate one in-app notification per relevant event/recipient, with deduplication. Make email preference channel-specific; persist state/event first and deliver email asynchronously so provider failure cannot roll back submission/review. A transactional outbox is a suitable delivery/retry boundary. |
| Desktop/mobile parity | This repository has no client or API contracts. | Serve both clients through the same authorization and domain operations; keep business rules server-side. The layouts and any missing visual feedback belong to the frontend/design analysis, not this backend template. |

## Suggested backend implementation sequence

1. **Make the application runnable and define contracts:** supply package/dependency metadata, environment validation, Express app composition, error handling, and route/API conventions. Resolve authentication identity and the frontend's expected transport and payloads before choosing endpoint details.
2. **Add schema through new migrations:** users/roles, mentor assignments, activities, submission versions, version-specific reviews, conversations/messages, notifications, email preferences, and an outbox (if asynchronous email is selected). Add foreign keys, uniqueness and query-supporting indexes for ownership, assignments, version numbering, idempotency, and event deduplication. Preserve migration `001-example` unchanged if it has been applied; the repository's documented checksum contract requires new migration versions.
3. **Implement scoped domain operations:** centralize assignment/ownership checks and lifecycle transition rules; apply those checks to list, detail, dashboard, submit, review, conversation, and notification reads/writes. Avoid relying on frontend hiding or list filtering as authorization.
4. **Add consistency and delivery guarantees:** conditional updates for optimistic concurrency; idempotent submission; review/version binding; atomic state + event persistence; deduplicated in-app notifications; retryable email delivery independent of the primary transaction.
5. **Expose and verify API capabilities:** student/mentor activity lists and detail, start/submit, mentor review/correction, dashboard aggregates, mentor directory (without cross-student activity access), conversations/messages, notification read state, and email preferences. Final route shapes should follow the actual frontend contract, which is not in this repository evidence.
